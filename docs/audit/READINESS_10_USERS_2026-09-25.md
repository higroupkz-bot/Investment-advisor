## 0. Вердикт

**Логически проект к 10 пользователям готов; до раунда `§−122` он к ним был НЕ
готов физически.** Все дефекты ниже невидимы для одного пользователя и проявляются
только при параллельных отчётах — то есть ровно в момент запуска. Шесть из них
закрыты кодом и гейтами в этом раунде; остальное — операции и решения владельца
(§5). Оценка готовности после раунда — **7.4 / 10** (была бы 5.5: бот замерзал
на минуту на каждый DEEP).

| **Эффективность** | **6.5** | 1 vCPU на всех: движок 2–4 мин CPU на отчёт; потолок ≈ 50–80 отчётов/день; RAG-этап 4 с на пустой базе; котировки грузились ДВАЖДЫ на отчёт (закрыто) |

## 1. Скрытые ошибки — найдены и закрыты (`§−122`)

| # | Где | Что было | Цена при 10 пользователях | Стало | Гейт |
|---|---|---|---|---|---|
| **H-1** 🔴 | `tg_bot._run_analysis_background`, Step 4 | `_build_pdf_payload` (RAG: ChromaDB + ONNX; LLM: HTTP к Anthropic 30–120 с) вызывался **в event loop**. Сценарная ветка ту же функцию оборачивала в executor — DEEP/BASE нет | Пока модель пишет нарратив одному, бот **не читает апдейты Telegram ни для кого**: /start, кнопки, статус-строки других отчётов — всё стоит. Health-сервер живёт в том же loop'е | `run_in_executor`, как в сценарной ветке | `test_payload_build_leaves_the_event_loop` |
| **H-2** 🔴 | `tg_bot._send_report` | `render_report_html` + `write_report_html` (340 КБ) + `upload_report` (PUT в GCS + подпись URL) — в loop'е | Секунды заморозки на КАЖДЫЙ отчёт, любого тира | executor | `test_render_and_upload_leave_the_event_loop` |
| **H-3** 🔴 | `tg_bot._analyze_existing_portfolio_sync` | Stage 2 строила `UniversalPortfolioManager()` с дефолтом `freedom`, тогда как Stage 1 — с `price_source=source` | Для `manual`/`demo` цены Stage 2 — **из Tradernet** (I-12: данные брокера не-клиенту), демо-отчёт зависел от сети и WAF, для всех — **второй сетевой поход** за теми же рядами (кэш промахивается: провайдер — часть ключа). Тест I-12 падал на первом конструкторе и до Stage 2 не доходил | источник прокинут; тест ждёт `[source, source]` | `test_every_stage_uses_the_chosen_price_source` |
| **H-4** 🟠 | нет общего потолка | Слот — по пользователю; 10 пользователей = 10 параллельных конвейеров на 1 vCPU, executor (≈5 потоков) занят ожиданием Anthropic | Каждый отчёт в 10 раз медленнее, executor исчерпан — vault/БД-операции встают в очередь за LLM | `MAX_CONCURRENT_REPORTS` (дефолт 2), очередь с сообщением «перед вами N» | `ReportGateTest` (+ мутация: без release гейт встаёт) |
| **H-5** 🟠 | аренда слота в SQLite, TTL 1800 с | Редеплой/падение посреди отчёта: аренда живёт ещё до 30 мин, новый инстанс её не снимает | Пользователь видит «анализ уже идёт» и не может повторить полчаса — после КАЖДОГО деплоя в момент чьего-то отчёта | по SIGTERM инстанс снимает СВОИ аренды (`release_report_locks_for_owner`) | `OwnerLeaseReleaseTest` |
| **H-6** 🟡 | `ai_narrative` | Клиент Anthropic без `timeout`: у SDK 600 с чтения × 3 попытки | Зависший ответ держит поток executor'а и слот пользователя до 30 мин | `ANTHROPIC_TIMEOUT_S` (300 с), фолбэк-нарратив вместо ожидания | `AnthropicTimeoutTest` |

**Проверено и верно (без правок):** слот пользователя атомарен в SQLite (`BEGIN IMMEDIATE`,
`ON CONFLICT … WHERE expires_at <= now`); `journal_mode=DELETE` (WAL на gcsfuse запрещён —
верно); списание ТОЛЬКО после доставки, все ветки отказа возвращают «не списан»; кэш истории
пишется через `tmp + os.replace`; локальная копия базы Stooq — через `.part + os.replace`;
`_SCENARIO_CACHE` ограничен (64 записей, TTL 1 ч); graceful shutdown освобождает
`getUpdates` за ≤3 с; секреты — из Secret Manager, образ под non-root; сеть при импорте
запрещена гейтом.

**Наблюдения без правок (не критично):**
- `fx_feed` пишет дисковый кэш не атомарно (`write_text`); чтение обёрнуто в `try` → в
  худшем случае повторный запрос к FRED.
- Пул executor'а по умолчанию `min(32, cpu_count+4)`; на Cloud Run `cpu_count()` — хост,
  не квота. Гейт H-4 делает размер пула несущественным.
- FSM онбординга — `MemoryStorage`: теряется при редеплое; черновик ручного ввода
  сохранён в БД (E-6), анкета — нет.
- 10 welcome-токенов × 10 пользователей = до 50 бесплатных DEEP ≈ $12 LLM — приемлемо.
- Cloud Run без явного startup/liveness probe: работает TCP-проба по умолчанию.

## 2. Архитектура и структура

- **Слои L0–L4 объявлены и под гейтами** (`test_layering`, `test_service_boundaries`):
  три границы конвейера (`results{}` → payload → design-data) пинятся тестами.
- **Два бота = два сервиса из одного образа**, изоляция по процессу, токену, файлам
  состояния и по коду (манифест корзин, `§−121`). Физический переезд — план С-1…С-3.
- **Долг:** `tg_bot.py` 4 000 строк без контракта (`_run_analysis_background` ≈ 400
  строк, десять веток выхода); `pdf_payload.build_payload` 900 строк; промпт 25 КБ вне
  тестового контура. Это стоимость правок, не риск запуска.
- **SSOT соблюдён:** тарифы, классификация, бренд, env — по одному месту с гейтами.

## 3. Масштабируемость — модель ёмкости

| Ресурс | Сейчас | Потолок | При 10 пользователях (≈20 отчётов/день) |
|---|---|---|---|
| CPU | 1 vCPU, always-on | ≈ 50–80 отчётов/день (Step 2 — 2–4 мин CPU) | ✅ запас ×3 |
| Параллельность | `MAX_CONCURRENT_REPORTS=2` + очередь | ждущий видит место в очереди | ✅ пиковые 5 одновременных → 3 ждут ≈ 3–6 мин |
| Executor | ≤2 длинных потока (LLM) + короткие | — | ✅ после H-1/H-4 |
| Брокер (Tradernet) | 6 потоков на отчёт, WAF по IP | 2 отчёта × 6 = 12 соединений | ⚠️ без статического egress каждый рестарт — риск блока |
| SQLite на gcsfuse | 1 писатель, `synchronous=FULL` | сотни мс на запись | ✅ единицы записей на отчёт |
| Память 2 GiB | движок + Chroma/ONNX в процессе | 2 отчёта × ~300 МБ + кэш | ✅; при `MAX_CONCURRENT_REPORTS≥4` мерить |
| LLM | 1 вызов/отчёт, $0.10–0.23 | лимиты Anthropic не близко | ✅ ≈ $20–40/мес |
| Один инстанс | `max-instances=1` | горизонтально — нет | ✅ для 10; 🔴 для 100+ (Cloud SQL, план §5) |

Шаг вверх (100+ пользователей) — не тюнинг, а миграция: Cloud SQL вместо SQLite на
gcsfuse, `max-instances>1` (аренда A-4 к этому готова), вынос RAG-эмбеддинга из процесса
бота. Это отдельный проект (`ECONOMICS.md §5`), для 10 пользователей он не нужен.

## 4. Оценка логики, эффективности, качества

**Логика — 8.5.** Конвейер отказоустойчив по построению: каждая стадия при отказе
сообщает код поддержки и «токен не списан»; списание — единственная точка после
доставки; демо бесплатно; слот атомарен. Математика сверена с деньгами (`§−121`).
Что не даёт выше: rf статичная; две форвардные доходности на странице (`§−121` план);
`ai_leverage_warning` — единственное место, где вердикт зависит от модели.

**Эффективность — 6.5.** 1 vCPU обслуживает движок, RAG-эмбеддинг, рендер и Telegram.
До раунда котировки грузились дважды, LLM держал loop. После — два отчёта параллельно,
остальные в очереди. Потолок известен и измерен ECONOMICS: 50–80 отчётов/день.
Prompt caching (L-12) не внедрён — −40% к стоимости LLM лежит на столе.

**Качество — 8.0.** 2 060+ тестов, две зеркальные верификации, каждый новый гейт с
мутацией, инварианты в исполняемых гейтах (AST-сканеры, манифесты, golden). Слабое место
— флоу бота: он тестируется стабами, живого многопользовательского прогона нет, а
`_run_analysis_background` — 400 строк без декомпозиции.
